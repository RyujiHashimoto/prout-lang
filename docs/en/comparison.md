# How Etsah compares

Etsah is a contract layer for an AI agent's declared tools. `etsah check` reads the source and reports whether that declaration is allowed to run. It does not run the agent, send mail, move money, or call a host.

This page compares that check with design-by-contract languages, effect systems, policy engines, LLM guardrails, and MCP tool annotations. Each row says what the public docs say that system checks, and when. The last column is the difference in this repository. It is not a ranking, and it is not a claim that the idea is new.

The Etsah rules used below are the ones in [SPEC.md](../../SPEC.md) and [the agent quickstart](agents-quickstart.md). A task's effects have to match the ops it calls. `policy external` marks an `emit` or `net` that needs a gate. Every `spend`, and every `write` marked `policy contract`, needs a gate too. The gate names a human role and the effect it holds. Budgets and hourly caps are declarations the checker compares. They are not live counters.

## What each system checks

| System | What it checks | When | Where Etsah differs |
|---|---|---|---|
| [Eiffel](https://www.eiffel.org/doc/eiffel/ET-_Design_by_Contract_%28tm%29%2C_Assertions_and_Exceptions) | Preconditions (`require`), postconditions (`ensure`), class invariants, and other assertions. The Eiffel introduction says contracts can be monitored at run time under compilation options. | Runtime, when assertion monitoring is turned on for the compilation. | Eiffel monitors a routine's assertions while the routine runs. Etsah does not execute the task. It accepts or rejects the declaration before a run. |
| [Dafny](https://github.com/dafny-lang/dafny/blob/master/docs/DafnyRef/Specifications.md) | `requires` and `ensures`. The reference says Dafny checks that preconditions are met at every call site, and that the implementation establishes the postcondition. The [tutorial](https://github.com/dafny-lang/dafny/blob/master/docs/OnlineTutorial/guide.md) shows a failed proof being rejected. | Static. The proof is attempted before the program is trusted to run. | Dafny proves that code meets a functional spec. Etsah does not prove that an `impl native` body matches its `eff` line. It checks the effects, budgets, and gates that were written down. |
| [Koka](https://koka-lang.github.io/koka/doc/book.html) | An effect type on every function. The language book (section 2.2) describes `total`, `exn`, `div`, `console`, `ndet`, and `io`, plus user-defined effect handlers that discharge an effect. | Static. The compiler tracks the effect as part of the type. | Koka's effects are the language's own effects and handlers. Etsah's effects are the agent's `read`, `write`, `net`, `spend`, and `emit`, and a missing approval gate is `E-POLICY`, not a missing handler. |
| [OPA and Rego](https://www.openpolicyagent.org/docs/latest/) | A query over structured input and data. The docs say that when software needs a policy decision it queries OPA and supplies JSON, and OPA evaluates that query against policies and data. [`opa check`](https://www.openpolicyagent.org/docs/latest/cli/) parses and compiles Rego. A successful check prints nothing. It does not evaluate a decision. | The decision is made when something queries OPA. `opa check` is an earlier parse and compile of the policy text. | A query answers one input document. Etsah walks the task's declared sequence of tool calls, the union of their effects, and whether the approval gate is on that task. |
| [Cedar](https://docs.cedarpolicy.com/) | Allow or deny for one request: principal, action, resource, and context. The guide says application code asks the authorization engine, "Is this request authorized?" [Schema validation](https://docs.cedarpolicy.com/policies/validation.html) compares a policy with a schema when the policy is created or updated. The same page says Cedar does not use the schema while it evaluates a request. | Authorization runs when the application asks. Schema validation runs when policies are written, separately from evaluation. | Cedar decides a single request. Etsah's `E-POLICY` is about the task as written: an external send, a payment, or a contract change with no gate on that task, or a host that is not allowlisted. |
| [NeMo Guardrails](https://docs.nvidia.com/nemo/guardrails/about-nemo-guardrails-library/rail-types) | Input rails before the LLM, retrieval rails on retrieved text, dialog rails on the conversation, execution rails on tool and function calls, and output rails on the model's reply. The rail-types page lists those stages and says execution rails control tool calls. | During the live interaction, at the stage each rail is attached to. | NeMo sees the running conversation and the call the model just made. Etsah never sees model text. It only sees the contract. |
| [Guardrails AI](https://github.com/guardrails-ai/guardrails/blob/main/README.md) | Input and output guards. The project README describes validators that run on LLM inputs and outputs, and shows `guard.validate` accepting or rejecting a string when it is called. | When the application calls `validate` or runs a Guard around a model call. | Guardrails judges generated text against a validator. Etsah judges declared effects and whether a person has to approve them. It does not score the reply. |
| [MCP tool annotations](https://modelcontextprotocol.org/specification/2026-07-28/server/tools) | Optional hints on a tool. The 2025-11-25 schema defines `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`, and says every property is a hint, not a guarantee. The [2026-07-28 tools page](https://modelcontextprotocol.org/specification/2026-07-28/server/tools) says clients must treat tool annotations as untrusted unless they come from a trusted server. | The protocol does not check the hints. A client may read them when it lists tools. | This repository's importer can copy a `true` hint onto an `eff` line and marks it `inferred`. The check still requires gates and an allowlist. A hint is not an approval. The mapping is in the [quickstart](agents-quickstart.md). |

## Why not a Cedar or OPA policy plus a wrapper?

A wrapper can call Cedar or OPA before each tool and allow or deny that call. That is a decision about one request: this principal, this action, this resource, or this JSON document. The OPA docs describe that shape (software queries OPA with structured input). The Cedar guide describes the same shape (application code asks "Is this request authorized?" before the operation).

Etsah checks the task as a sequence. The task names every op it calls, and the checker requires the task's `eff` list to be the union of those ops' effects. It then asks whether an approval gate is placed on the task, covering an external `emit`, an external `net`, a `spend`, or a contract `write`, before that task is eligible to run. A policy that allows `mail.send` for the support agent does not, by itself, record that the send is the second call in a task that also reads a ticket, or that a person has to be named on the task before either call is acceptable. The per-run and per-period spend budget, and the hourly `net` and `emit` caps, are also compared across the task's declaration rather than on a single call.

A wrapper is still the right place to allow or deny a real call at the moment it happens. Etsah does not replace that. It rejects a declaration that is already unsafe, and it does so before the agent is started. The check does not prove the wrapper will ask, and it does not prove that `on_approved` is the only call that performs the gated effect. The task has to name the gate, and the gate's `before` list has to include the effect.

## What the Etsah check does not do

- It does not run cron, send mail, charge a card, cancel a subscription, or store idempotency keys.
- The checker does not count remaining budget. An integer-yen budget in the source is a declared ceiling. `etsah guard` does count `limit calls` and `limit spend`.
- It does not prove that the native implementation performs only the effects on the `eff` line.
- It does not treat an MCP hint as permission. A missing hint adds no effect. A guessed effect is a `review` comment, and comments do not change the check.
- Information-flow labels (`String @pii`, sink policies, `sends`, `declassify`) are checked statically when a program declares them. [SPEC.md](../../SPEC.md) limits that check to declared label sets: implicit flow, collection element labels, label polymorphism, and runtime enforcement are out of scope. Programs with no labels keep the same AST hash. The design notes are in [docs/information-flow.md](../information-flow.md).
